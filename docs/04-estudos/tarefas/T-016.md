# Diário de estudo — T-016

## O que foi feito

Uma tarefa diferente das outras: em vez de construir algo, foi um **pente-fino** de testes em tudo o que já tinha sido entregue (T-007 a T-012). O pedido do George: **5 cenários por funcionalidade** (caminho feliz, bordas e erros) em cada nível de teste, para achar bugs. A tabela da tarefa lista 14 funcionalidades, da navegação e do menu até a API de saúde.

A regra principal: **nenhum código de produção muda**. Quando um teste mostra um bug, ele não é corrigido aqui. O teste fica marcado como "bug conhecido" (`it.fails` no Vitest, `test.fail` no Playwright), com um comentário que explica o bug. Assim a suíte continua verde, e cada bug vira uma tarefa nova no backlog.

Divisão do trabalho:

- **dev**: testes unitários do front e da API, junto do código. Criou arquivos novos (`acessibilidade.test.tsx`, `responsividade.test.ts`, `Atalho.test.tsx`, `criar-app.spec.ts`) e um apoio de testes (`capturar-erros-de-renderizacao.ts`). Achou 4 bugs (BUG-1 a BUG-4).
- **code-reviewer**: conferiu que só testes mudaram e que cada `it.fails` corresponde a um bug real. Aprovou com 5 sugestões opcionais.
- **qa**: testes de rota da API (Supertest) e de ponta a ponta (Playwright), com 3 arquivos e2e novos (`tema.spec.ts`, `acessibilidade.spec.ts`, `seguranca.spec.ts`). Achou mais 5 bugs (BUG-Q1 a BUG-Q5). A primeira execução do qa foi interrompida; o trabalho parcial foi guardado, revisado e aproveitado na retomada.

Resultado: **9 bugs + 1 erro** viraram tarefas. Exemplos: a página inteira some se a API mandar um projeto fora do formato (BUG-1); abrir o site direto em `/#servicos` deixa a página no topo (BUG-Q2); uma palavra longa no título de um projeto faz a página rolar para o lado no celular (BUG-Q4).

## Conceitos

- **tipos-de-teste-unitario-rota-e2e**: o mesmo comportamento pode ser testado em três alturas. O unitário testa uma peça sozinha (rápido, aponta o defeito exato). O de rota sobe a API em memória e faz requisições HTTP. O e2e abre o navegador de verdade. *Por quê aqui:* cada nível achou bugs que os outros não achariam. O BOM no `projetos.json` (BUG-4) só aparece no unitário de leitura do arquivo; o menu que passa da tela em 568x320 (BUG-Q3) só aparece com layout real, no navegador.
- **teste-de-regressao**: um teste que confere se algo que **já funcionava continua funcionando**. "Regressão" é quando uma mudança nova quebra uma coisa antiga. *Por quê aqui:* o pente-fino revisitou as entregas da T-007 à T-012. Os testes novos passam a vigiar esse comportamento em toda tarefa futura, sem ninguém precisar lembrar de conferir à mão.
- **bug-conhecido-com-it-fails-e-test-fail**: `it.fails(...)` (Vitest) e `test.fail()` (Playwright) invertem o resultado: o teste **passa quando falha**. Se um dia o bug for corrigido, o teste "quebra" e avisa que a marcação pode sair. *Por quê aqui:* a tarefa proibia corrigir código, mas o bug precisava ficar registrado num teste executável, com a suíte verde. O `test.fail` também aceita uma **condição**: em `pagina-inicial.spec.ts`, o teste do título da aba só é marcado como "esperado falhar" quando o `<title>` do `index.html` difere do nome no arquivo de conteúdo (troca de nome pela metade, da T-015).
- **controle-negativo-em-testes**: rodar o teste na situação errada para provar que ele detecta o problema. *Por quê aqui:* um `it.fails` passa se o teste falhar por **qualquer** motivo, inclusive um erro de digitação no próprio teste. Esse é o "falso positivo" que o code-reviewer apontou. Por isso dev e qa conferiram cada bug **sem a marcação**, para ver que a falha era pelo motivo descrito. O qa também corrigiu o teste do BUG-Q1, que falhava pelo motivo errado.
- **error-boundary**: um componente React que "segura" o erro de um filho e mostra uma mensagem no lugar, em vez de desmontar a árvore toda. *Por quê aqui:* sem ele, um único `CartaoDeProjeto` que lança erro (projeto sem `stacks`, BUG-1; data inválida em `Intl.DateTimeFormat`, BUG-2) apaga a página inteira, inclusive o `<h1>`. O RF-05 pede uma mensagem amigável só na seção Projetos.
- **erros-nao-tratados-no-vitest**: quando um componente lança um erro durante uma atualização assíncrona (ex.: a resposta da API chegou), o React o repassa ao `window`. O Vitest trata isso como "erro solto" e deixa a execução vermelha, **mesmo** com o teste marcado com `it.fails`. *Por quê aqui:* o dev criou `capturarErrosDeRenderizacao()`, que liga um ouvinte de `error` no `window` (com `preventDefault`) e silencia o `console.error` enquanto o teste roda. Assim o erro conta como tratado pelo teste.
- **chave-key-no-react**: ao desenhar uma lista, o React usa `key` para saber qual item é qual entre uma renderização e outra; a chave tem que ser única entre irmãos. *Por quê aqui:* `Projetos` usa `key={projeto.titulo}`, e a validação da API não recusa títulos repetidos (BUG-3). Dois projetos com o mesmo título geram aviso de chave duplicada e podem trocar de lugar na tela. Onde corrigir (chave no front ou recusar na API) é escolha do George.
- **bom-em-utf-8**: o BOM (*byte order mark*, caractere invisível U+FEFF) é uma marca que alguns editores do Windows gravam no início de arquivos "UTF-8 com BOM". *Por quê aqui:* o `readFileSync` mantém o BOM e o `JSON.parse` não o aceita. Basta salvar o `projetos.json` com essa opção para a API não subir (BUG-4). O teste cria o BOM com `String.fromCharCode(0xfeff)`, porque ele é invisível no código.
- **estouro-horizontal-em-grade-css**: numa grade, a largura mínima de uma coluna `1fr` (que na prática é `minmax(auto, 1fr)`) ou de uma coluna implícita (`auto`) é o tamanho do maior conteúdo que não quebra. Uma palavra sem espaço (um endereço, um nome de classe) alarga o card além da tela. *Por quê aqui:* é o BUG-Q4. Em `Projetos.module.css`, a partir de 36rem a lista já usa `repeat(2, minmax(0, 1fr))`, que deixa a coluna encolher. No celular, porém, a `.lista` não define colunas: fica uma coluna implícita, que cresce até caber a palavra. O `overflow-wrap: break-word` do `body` não basta, porque o item da grade cresce antes de o texto quebrar. O e2e mede isso com `medirEstouroHorizontal` em 360px (RNF-01).
- **rolagem-ate-ancora-em-spa**: ao abrir `/#servicos`, o navegador procura o elemento `id="servicos"` assim que o HTML chega. Numa SPA, o HTML chega quase vazio: as seções só existem depois que o React monta a página, e ninguém rola até elas depois disso. *Por quê aqui:* é o BUG-Q2 (achado da T-012). O teste antigo não pegava o problema porque abria `/` antes e só depois trocava a âncora na mesma página. O teste novo abre a âncora na **primeira** visita, como quem recebe um link compartilhado.
- **cabecalhos-de-seguranca-http**: cabeçalhos que a API manda em toda resposta para reduzir riscos. `X-Powered-By: Express` (padrão do Express) revela a tecnologia do servidor. A falta de `X-Content-Type-Options: nosniff` deixa o navegador "adivinhar" o tipo da resposta. *Por quê aqui:* é o BUG-Q5, testado em `health.e2e-spec.ts`. A biblioteca `helmet` resolve os dois de uma vez, mas é dependência nova (decisão do George). A alternativa é um ajuste manual no Express.
- **testes-instaveis-e-repeat-each**: um teste instável (*flaky*) às vezes passa e às vezes falha sem nada mudar, normalmente por causa de tempo ou de ordem. *Por quê aqui:* o qa rodou o e2e com `--repeat-each=3` (cada teste 3 vezes, 750 execuções) e as rotas em 3 rodadas, para garantir que os testes novos e os `test.fail` são estáveis antes de entrarem na suíte de todo dia.
