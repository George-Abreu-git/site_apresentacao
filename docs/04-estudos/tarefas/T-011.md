# Diário de estudo — T-011

## O que foi feito

Na T-010, o `GET /api/projetos` devolvia só o que o George escreveu no arquivo curado (`apps/api/conteudo/projetos.json`). A T-011 completou cada projeto com **dados vivos** do GitHub: **linguagem principal, estrelas e data do último push** (RF-06, parte 2). Foi a primeira vez que a API **chama outro serviço pela internet**.

O caminho de uma requisição ficou assim:

1. O `ProjetosService` pega a lista curada e, para cada projeto com `repositorio`, pede os dados vivos ao `GithubService`, **todos ao mesmo tempo**.
2. O `GithubService` descobre se o endereço é do GitHub (`github.com/<dono>/<nome>`). Se for do GitLab, por exemplo, o projeto segue só com os dados curados.
3. Se os dados desse repositório estão no **cache** e ainda valem, usa o cache. Se não, o `GithubCliente` chama `https://api.github.com/repos/<dono>/<nome>` com o `fetch` do Node, com **tempo limite de 5 s**.
4. Deu certo: guarda no cache por `GITHUB_CACHE_TTL_SEGUNDOS` (padrão 3600 s, ou seja, 1 hora) e devolve `github: { disponivel: true, linguagem, estrelas, ultimaAtualizacao }`.
5. Deu errado (GitHub fora do ar, lento, limite atingido, repositório inexistente, resposta estranha): **não dá erro**. O projeto sai com `github: { disponivel: false }`, a rota responde 200 e o log ganha um aviso, **sem o token**.

A tarefa nasceu `eu-faco` (integração com API externa é foco de aprendizado), mas o George passou todas as tarefas restantes para `agente-faz` em 2026-10-15; o aprendizado fica neste diário. O dev implementou com 56 testes unitários novos ou alterados, o code-reviewer aprovou sem ajustes e o qa escreveu os testes de rota (API com 142 testes verdes no fim). Ficaram pendentes para outras tarefas: `GITHUB_CACHE_TTL_SEGUNDOS` no `.env.example` e no Render (T-013) e o formato de `Projeto.github`, que a T-012 (front) vai consumir.

## Conceitos

- **fetch-nativo-e-tempo-limite**: o Node já traz o `fetch` (o mesmo do navegador), então não foi preciso instalar biblioteca. Três detalhes: (1) o `fetch` **só lança erro em falha de rede**; um 404 ou 403 chega como resposta normal, por isso o código confere `resposta.ok` (verdadeiro para status 200-299); (2) cabeçalhos: o GitHub **recusa requisição sem `User-Agent`** e recomenda fixar a versão da API (`X-GitHub-Api-Version`); (3) `signal: AbortSignal.timeout(5000)` cancela a requisição depois de 5 s. *Por quê aqui:* sem o tempo limite, um GitHub lento seguraria a resposta de `/api/projetos` indefinidamente, e o site ficaria esperando.
- **cache-com-ttl**: `CacheComValidade` é um `Map` em que cada valor guarda também a hora em que vence (`expiraEm = agora + validade`). TTL = *time to live*, "tempo de vida". O relógio (`agora`) entra pelo construtor, com `Date.now()` como padrão, para os testes avançarem o tempo sem esperar de verdade. *Por quê aqui:* sem token, o GitHub aceita só **60 requisições por hora**; sem cache, cada visita ao site gastaria uma por projeto. Com 1 hora de validade e 10 projetos, são no máximo 10 consultas por hora. Detalhes que a revisão apontou para o futuro: **falhas não vão para o cache** (assim que o GitHub volta, os dados voltam; o preço é tentar de novo a cada requisição enquanto ele está fora), não há proteção contra **cache stampede** (várias requisições ao mesmo tempo com o cache vazio buscam o mesmo repositório) e uma alternativa seria **stale-if-error** (servir o último dado conhecido, mesmo vencido, quando o GitHub falha).
- **fallback-e-degradacao-graciosa**: fallback é o "plano B". O `GithubService.dadosVivos` **nunca lança erro**: captura qualquer falha do cliente e devolve `{ disponivel: false }`. O site **degrada com elegância**: perde as estrelas, mas mostra os projetos. *Por quê aqui:* o GitHub é um serviço de fora, que o projeto não controla. Se uma falha dele virasse erro 500, a seção de projetos inteira sumiria por causa de um detalhe. O cliente traduz todas as falhas para um único erro (`GithubIndisponivelError`), com uma mensagem por motivo (403/429 = limite atingido, 404 = não encontrado, 401 = token recusado), para o service tratar tudo do mesmo jeito.
- **segredo-em-variavel-de-ambiente**: o `GITHUB_TOKEN` é lido de `process.env` e vai **só** no cabeçalho `Authorization: Bearer ...` da chamada ao GitHub. Nenhuma mensagem de erro ou de log é montada com os cabeçalhos, e a resposta da API nunca o inclui. Variável vazia (`GITHUB_TOKEN=`) conta como ausente. *Por quê aqui:* é o RNF-05. Um token no código vai para o GitHub público; um token no log fica visível para quem lê o painel do Render. O token é **opcional**: sem ele a API funciona, só com o limite menor.
- **uniao-discriminada**: `DadosVivosDoGithub = ({ disponivel: true } & DadosDoGithub) | { disponivel: false }`. O campo `disponivel` é o **discriminante**: depois de um `if (github.disponivel)`, o TypeScript sabe que `estrelas` existe; no `else`, sabe que não existe. *Por quê aqui:* o front (T-012) é **obrigado** a tratar o caso "GitHub ausente" antes de ler as estrelas, e o compilador avisa se esquecer. Junto veio o **`Omit<T, K>`**: `ProjetoCurado = Omit<Projeto, 'github'>` é o `Projeto` sem o campo `github`, e a validação do arquivo curado recusa esse campo. Assim o arquivo curado não consegue "inventar" dados vivos.
- **promise-all**: `Promise.all(this.projetos.map((p) => this.completar(p)))` dispara as consultas **ao mesmo tempo** e espera todas. O resultado vem **na ordem da lista de entrada**, não na ordem em que cada consulta terminou. *Por quê aqui:* com 10 projetos e o GitHub levando 300 ms cada, em sequência seriam 3 s; em paralelo, uns 300 ms. E a ordem escolhida pelo George no arquivo curado se mantém. O `Promise.all` falharia inteiro se uma promessa rejeitasse; aqui isso não acontece porque `dadosVivos` nunca lança erro (o fallback acima).
- **injecao-de-dependencia-no-nestjs**: o `GithubModule` tem `GithubCliente`, `GithubService` e a configuração, mas **exporta só o `GithubService`** (`exports: [GithubService]`). O `ProjetosModule` importa o `GithubModule` e o `ProjetosService` recebe o `GithubService` no construtor, pelo tipo. *Por quê aqui:* é o monolito modular da ADR-0001: o domínio `projetos` usa o domínio `github` só pela porta que ele expõe; cliente HTTP e configuração ficam escondidos. O módulo não tem controller, porque não expõe rota própria.
- **provider-de-fabrica-e-fail-fast**: a configuração entra pelo token `GITHUB_CONFIGURACAO` com `useFactory: () => lerConfiguracaoDoGithub()`, o mesmo padrão do `PROJETOS_CURADOS` da T-010. *Por quê aqui:* se `GITHUB_CACHE_TTL_SEGUNDOS` vier errado (`0`, `-5`, `1.5`, `10s`, `abc`), a API **nem sobe** e diz o motivo. A validação usa `/^\d+$/` (só dígitos) porque `parseInt('10s')` daria `10` e esconderia o erro de digitação.
- **validacao-em-tempo-de-execucao-com-type-guards**: a resposta do GitHub entra como `unknown`, igual ao arquivo curado da T-010: `traduzirResposta` confere `language` (texto ou `null`), `stargazers_count` (número) e `pushed_at` (texto) antes de usar. Na leitura do endereço, `URL.canParse` diz se o texto é um endereço válido sem precisar de `try/catch`, e o hospedeiro é comparado inteiro (`github.com` ou `www.github.com`), o que barra imitações como `github.com.exemplo.com`. *Por quê aqui:* dados de fora da API podem vir em qualquer formato; uma mudança na API do GitHub vira `{ disponivel: false }`, não um card quebrado. A escolha de `pushed_at` (último envio de código) em vez de `updated_at` (que muda até com uma estrela nova) também está comentada no código.
- **simular-fronteira-externa-nos-testes**: nenhum teste vai ao GitHub de verdade. O qa simula **só o `fetch` global**, a "internet" (`vi.spyOn(globalThis, 'fetch')`), e deixa o resto da API real: endereço, cabeçalhos, tradução, cache e fallback são todos exercitados. Ferramentas usadas: `vi.stubEnv` para variáveis de ambiente (desfeito com `vi.unstubAllEnvs`), `vi.useFakeTimers({ toFake: ['Date'] })` + `vi.setSystemTime` para "pular" 1 hora e ver o cache vencer, um `LogEmMemoria` (um `LoggerService` próprio) para procurar o token no log e `it.each` para os 10 tipos de falha. Cada simulação cria uma `Response` nova porque **o corpo de uma `Response` só pode ser lido uma vez**. *Por quê aqui:* testes que dependem do GitHub real falham sem internet, gastam o limite de requisições e não conseguem reproduzir "GitHub fora do ar" quando quiserem.
- **tipos-de-teste-unitario-rota-e2e**: o **dev** testou peças isoladas (configuração, leitura do endereço, cache com relógio controlado, cliente e service). O **qa** testou a **rota** com Supertest e a API inteira montada. Na rodada, 2 testes de rota antigos da T-010 quebraram, de propósito: comparavam a resposta com o JSON cru do arquivo, e agora ela tem o campo `github`. O dev os deixou para o qa (a pasta `apps/api/test/` é dele), que os ajustou com o apoio `semGithub`. *Por quê aqui:* mostra que mudar o formato de uma resposta afeta testes de outra tarefa, e que cada agente mexe só nos testes da sua área.

## Onde aparece no projeto

- `apps/api/src/github/github-cliente.ts`: `fetch`, `AbortSignal.timeout`, cabeçalhos, `resposta.ok`, `GithubIndisponivelError`, `motivoDoStatus` e `traduzirResposta`.
- `apps/api/src/github/github.service.ts`: cache por repositório (chave em minúsculas), fallback `{ disponivel: false }` e o aviso no log.
- `apps/api/src/github/cache-com-validade.ts`: o `Map` com `expiraEm` e o relógio injetável.
- `apps/api/src/github/configuracao-do-github.ts`: `GITHUB_TOKEN`, `GITHUB_CACHE_TTL_SEGUNDOS`, padrão de 3600 s, tempo limite de 5 s e `ConfiguracaoDoGithubInvalidaError`.
- `apps/api/src/github/repositorio-do-github.ts`: `extrairRepositorioDoGithub` com `URL.canParse`.
- `apps/api/src/github/github.module.ts`: providers, fábrica da configuração e `exports: [GithubService]`.
- `apps/api/src/github/*.spec.ts`: testes unitários do dev.
- `apps/api/src/projetos/projetos.service.ts`: `Promise.all` e a junção dos dados curados com os vivos.
- `apps/api/src/projetos/projeto-curado.ts`: `ProjetoCurado = Omit<Projeto, 'github'>`.
- `packages/shared/src/projeto.ts`: `DadosDoGithub`, a união `DadosVivosDoGithub` e o campo opcional `github` em `Projeto`.
- `apps/api/conteudo/README.md`: formato da resposta e variáveis de ambiente.
- `apps/api/test/github.e2e-spec.ts`: testes de rota do qa (dados vivos, cache, plano B, token).
- `apps/api/test/apoio/github-simulado.ts`: `simularGithub`, `respostaJson`, `LogEmMemoria` e `semGithub`.

## Exercícios

1. **Ver o cache e o plano B funcionando:** suba a API (`npm run dev -w apps/api`) e chame `GET /api/projetos` duas vezes. Compare o tempo das duas respostas: por que a segunda é mais rápida, e por quanto tempo isso vale? Depois desligue a internet (ou troque, só no seu teste, `ENDERECO_DA_API_DO_GITHUB` por um endereço que não existe) e reinicie a API: o que a resposta traz no campo `github`, qual é o status HTTP e o que aparece no log? Por que reiniciar foi necessário para ver isso (dica: onde o cache vive)? Desfaça a mudança no fim.
2. **União discriminada na prática:** num arquivo de teste qualquer, declare `const g: DadosVivosDoGithub = { disponivel: false };` e tente ler `g.estrelas`. Leia o erro do TypeScript. Depois envolva a leitura num `if (g.disponivel) { ... }` e veja o erro sumir. Responda: o que aconteceria na T-012 se o tipo fosse só `{ disponivel: boolean; estrelas?: number }`? Que erro o compilador deixaria de pegar?
