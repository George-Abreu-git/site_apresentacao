# Diário de estudo — T-018

## O que foi feito

A tarefa corrigiu o BUG-1, achado no pente-fino de testes da T-016. Se a API devolvesse em `GET /api/projetos` um projeto fora do formato (por exemplo, sem o campo `stacks`), o `CartaoDeProjeto` lançava erro ao desenhar. Como nada segurava esse erro, o React desmontava a **página inteira**: tela em branco, sem nem o `<h1>` com o nome do George. O front só conferia se a resposta era uma lista e confiava no resto.

A correção pôs **duas proteções**, uma atrás da outra:

1. **Na causa, conferir os dados.** Uma função nova, `ehProjeto`, confere cada item da resposta: os campos obrigatórios têm o tipo certo, os opcionais (inclusive `github`) também, e os links (`repositorio`, `demo`) só podem começar com `http://` ou `https://`, porque viram `href` no card. Campos a mais são aceitos, para a API poder crescer sem quebrar o front. Basta um item inválido para a resposta inteira ser recusada, e a seção mostra a mensagem de erro que já existia.
2. **Na consequência, conter o estrago.** Um componente novo, `LimiteDeErro` (um *error boundary*), envolve a lista de cards. Se algum card lançar erro ao desenhar mesmo com os dados conferidos, só os cards somem e o aviso da seção passa a mostrar a mensagem de erro. O resto da página continua de pé.

O teste que documentava o bug com `it.fails` em `App.test.tsx` virou um teste normal (e mais rigoroso). O dev escreveu 14 cenários novos (unitários e de componente). O qa escreveu 5 cenários e2e com Playwright, para celular e desktop, provou que eles **falham** no código antigo e passam no novo, e repetiu a suíte 5 vezes seguidas para ver se ela era estável (60 de 60). O qa também reescreveu `seguranca.spec.ts`: agora um endereço não http(s) vindo da API nem chega a virar link.

## Conceitos

- **validacao-em-tempo-de-execucao-com-type-guards**: uma *type guard* é uma função que devolve `valor is Projeto`. Ela recebe algo do tipo `unknown`, confere campo por campo e, quando devolve `true`, o TypeScript passa a tratar o valor como `Projeto` sem precisar de `as`. Detalhe útil: `typeof null` e `typeof []` também dão `"object"`, por isso `ehObjeto` faz duas checagens a mais. *Por quê aqui:* o `resposta.json()` devolve qualquer coisa. Declarar o retorno como `Projeto[]` não confere nada: é só uma promessa ao compilador. A API já tinha uma validação parecida (`validar-projetos-curados.ts`, T-010), mas com outro propósito (conferir o arquivo de projetos curados na subida). Unificar as duas em `packages/shared` ficou como ideia para o George decidir, porque hoje o pacote só tem tipos.
- **import-type-e-apagamento-de-tipos**: os tipos do TypeScript **somem** quando o código vira JavaScript. *Por quê aqui:* o tipo `Projeto` é compartilhado entre a API e o front (`packages/shared`), mas isso só garante que os dois lados *compilam* de acordo. Em tempo de execução, nada impede a API (ou um proxy no caminho) de mandar outra coisa. É a mesma regra da T-017 vista pelo outro lado: lá ela foi uma vantagem (ninguém precisa da `dist/`); aqui ela é o motivo de conferir os dados na mão.
- **error-boundary**: um componente que segura o erro lançado por um filho **durante a renderização**. Sem ele, o React desmonta a árvore inteira. Precisa ser um componente de **classe**, porque o React ainda não tem hook para isso: `static getDerivedStateFromError` calcula o novo estado (`falhou: true`) sem efeitos colaterais, e `componentDidCatch` roda depois e pode avisar o pai (aqui, chama `aoFalhar`). Ele **não** pega erros de `onClick`, `fetch` ou `setTimeout`, que não acontecem durante a renderização. *Por quê aqui:* é o que transforma "tela em branco" em "só a seção Projetos mostra um aviso". O limite não desenha a mensagem sozinho (devolve `null`): quem o usa decide o que mostrar, e o `Projetos` liga `falhouAoMostrarOsCards` para trocar o texto do aviso.
- **defesa-em-profundidade**: várias camadas de proteção, cada uma pegando o que a anterior deixar passar. *Por quê aqui:* a validação resolve a causa conhecida (dado fora do formato), mas não pega tudo. Um dado com o formato certo ainda pode quebrar o card (o BUG-2, uma data que é texto mas não é data, fica para a T-019). O error boundary é a segunda camada: qualquer erro de desenho fica contido na seção. O mesmo princípio apareceu nos hooks da T-001.
- **esquemas-permitidos-em-href**: um `href="javascript:alert(1)"` executa código quando alguém clica. A defesa é uma **lista de permissões** (*allowlist*): só aceitar o que começa com `http://` ou `https://` (sem diferenciar maiúsculas, por causa do `/i`), em vez de tentar listar tudo o que é perigoso (`javascript:`, `JAVASCRIPT:`, `data:`, com espaço antes...). *Por quê aqui:* `repositorio` e `demo` viram links no card. Os testes do qa em `seguranca.spec.ts` tentam justamente as variações que uma lista de bloqueio esqueceria.
- **regiao-viva-aria**: o `<p role="status">` da seção é uma região viva. Quando o texto dentro dele muda, o leitor de tela lê a novidade sem mover o foco. *Por quê aqui:* quando o card quebra, o aviso passa de vazio para a mensagem de erro, e quem usa leitor de tela fica sabendo. A região fica sempre na página (mesmo vazia), porque o leitor de tela só acompanha regiões que já existiam antes da mudança.
- **bug-conhecido-com-it-fails-e-test-fail**: na T-016, o BUG-1 foi registrado com `it.fails`, um teste que **deve** falhar enquanto o bug existir. *Por quê aqui:* quando a correção entra, o `it.fails` passa a "falhar ao falhar", e isso obriga a convertê-lo num teste normal (critério de aceite da tarefa). Um cuidado apontado na revisão: dois testes novos usam o BUG-2 para provocar o erro no card. Quando a T-019 corrigir esse bug, eles precisam de outra forma de provocar o erro (ex.: `vi.mock` do `CartaoDeProjeto`). Teste apoiado num bug conhecido fica acoplado a ele, e o aviso foi anotado na T-019.
- **injetar-falha-no-navegador-com-addinitscript**: `page.addInitScript` roda um script na página **antes** do código do site. O qa usou isso para fazer `Intl.NumberFormat.prototype.format` lançar erro só para um número "marcado" de estrelas (4.040.404). *Por quê aqui:* era preciso provar no e2e que um erro ao desenhar o card fica contido, sem depender de um bug real (o BUG-2 vai sumir). Junto, o teste observa três coisas diferentes: `pageerror` (exceção não tratada na página), `console.error` e diálogos (`alert`). Um erro segurado pelo error boundary não vira `pageerror`.
- **controle-negativo-em-testes**: rodar o teste contra a versão errada para ver se ele falha. *Por quê aqui:* o qa fez uma "mutação manual" (voltou o código da `main`) e os 6 testes e2e falharam; com a correção, passaram. Um teste que nunca falhou não prova nada.
- **testes-instaveis-e-repeat-each**: `--repeat-each=5` roda cada teste 5 vezes seguidas. *Por quê aqui:* testes com tempo (esperar o aviso mudar) podem passar por sorte. 60 de 60 dá mais confiança de que o teste não é instável (*flaky*).
- **tipos-de-teste-unitario-rota-e2e**: cada camada testou o que lhe cabia. Unitário: `ehProjeto` e `buscarProjetos`. Componente: `LimiteDeErro`, `Projetos` e `App`. E2e: a página real no navegador, no celular e no desktop, sem rolagem horizontal.

## Onde aparece no projeto

- `apps/web/src/api/formato-do-projeto.ts`: `ehProjeto` e as funções auxiliares (`ehObjeto`, `ehListaDeTextos`, `opcional`, `ehEnderecoHttp`, `ehDadosVivosDoGithub`).
- `apps/web/src/api/formato-do-projeto.test.ts`: os 5 cenários da validação.

- `apps/web/src/componentes/LimiteDeErro/LimiteDeErro.tsx` e `LimiteDeErro.test.tsx`: o error boundary de classe.
- `apps/web/src/componentes/Projetos/Projetos.tsx`: `<LimiteDeErro aoFalhar=...>` em volta da lista e o `role="status"` que troca para `textos.erro`.

- `e2e/testes/seguranca.spec.ts`: endereço não http(s) da API não vira link.
