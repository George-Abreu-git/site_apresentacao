# Diário de estudo — T-019

## O que foi feito

A tarefa corrigiu o BUG-2, achado no pente-fino de testes da T-016. A API lê o campo `pushed_at` do GitHub (a data do último envio de código) e o repassa ao front como `ultimaAtualizacao`. O problema: ela aceitava **qualquer texto** ali. No front, o card de projeto formata essa data com `Intl.DateTimeFormat`, e com um texto que não é data o `format` lança `RangeError: Invalid time value`. Como esse erro acontece durante o desenho do card, a página inteira sumia (antes da T-018; depois dela, o error boundary segurava o erro, mas os cards ainda sumiam).

A correção atacou o bug dos dois lados:

1. **Na API, recusar o dado ruim na entrada.** Em `github-cliente.ts`, uma função nova, `ehDataEHoraIso`, confere se `pushed_at` é mesmo uma data e hora no formato ISO 8601 com fuso (ex.: `2026-10-01T12:00:00Z`). Se não for, a resposta do GitHub é tratada como "formato inesperado", igual a quando falta a linguagem ou as estrelas, e o projeto aparece com `github: { disponivel: false }`. O resto do projeto (título, descrição, stacks) continua.
2. **No card, não quebrar mesmo se o dado ruim chegar.** Em `CartaoDeProjeto.tsx`, a data foi para um subcomponente, `UltimaAtualizacao`, que usa a função `formatarData`. Se a data for inválida, `formatarData` devolve `null` e o par "Atualizado em" some do card. Linguagem, estrelas e links continuam aparecendo. Com data válida, nada muda na tela.

Também houve trabalho nos testes. Os dois `it.fails` que documentavam o BUG-2 viraram testes normais. E dois testes da T-018 usavam justamente a data inválida para fazer o card lançar erro (para provar que o error boundary segura a falha). Com o bug corrigido, eles ficaram vermelhos. O dev trocou essa "muleta" por um **card simulado** com `vi.mock`, que lança erro só para um título combinado. O qa escreveu 16 testes de rota (9 datas inválidas, outros repositórios não afetados, falha que não fica no cache, aviso no log sem o token, 4 datas válidas que passam) e 5 cenários e2e no celular e no desktop, e mostrou que eles falham com o código antigo.

## Conceitos

- **validacao-em-tempo-de-execucao-com-type-guards**: `ehDataEHoraIso(valor: unknown): valor is string` é uma *type guard*. Quando devolve `true`, o TypeScript passa a tratar `pushed_at` como `string`. *Por quê aqui:* o corpo da resposta do GitHub chega como `unknown`; o tipo `DadosDoGithub` promete ao front uma data válida, e só uma conferência em tempo de execução cumpre essa promessa. É o mesmo padrão da `ehProjeto` da T-018, agora do lado da API, na **fronteira** onde o dado externo entra.
- **iso-8601-e-date-parse**: ISO 8601 é o formato padrão de data e hora em texto (`AAAA-MM-DDTHH:MM:SSZ`), o que o GitHub envia. `Date.parse(texto)` devolve o número de milissegundos ou `NaN` se não conseguir ler. *Por quê aqui:* `Date.parse` sozinho é generoso demais: ele aceita `"1"` (vira 01/01/2001). Por isso a API combina duas conferências. Limite que a revisão e o qa anotaram: o `Date.parse` do V8 (Node e Chrome) aceita dias que não existem, como `2026-02-30`, e os empurra para o mês seguinte. Isso não quebra o card (vira uma data válida), então ficou como observação fora do escopo.
- **expressoes-regulares-com-ancoras**: a regex `DATA_E_HORA_ISO` começa com `^` e termina com `$`, que "ancoram" o padrão no início e no fim do texto. Sem as âncoras, um texto como `"lixo 2026-10-01T12:00:00Z lixo"` passaria, porque a regex acharia a data no meio. *Por quê aqui:* a regex garante a **forma** (dígitos nos lugares certos, fuso `Z` ou `+03:00`, fração de segundo opcional), mas não o **significado**: ela aceita `2026-13-01T25:00:00Z` (mês 13, hora 25). O `Date.parse` cobre essa parte. Cada conferência tapa o buraco da outra.
- **intl-datetimeformat-e-rangeerror**: `Intl.DateTimeFormat` formata datas no padrão do idioma (em pt-BR, `01/10/2026`). Com um `Date` inválido (aquele cujo `getTime()` é `NaN`), o `format` não devolve um texto vazio: ele **lança** `RangeError`. *Por quê aqui:* era essa exceção que derrubava o card. `formatarData` confere `Number.isNaN(data.getTime())` antes de formatar e devolve `null` no lugar de lançar.
- **defesa-em-profundidade**: a API já recusa datas inválidas, mas o card se protege de novo. *Por quê aqui:* o front não deve depender de a API estar sempre certa (uma versão antiga da API, um proxy, um teste). São três camadas agora: a API filtra, o card omite a data ruim e, se mesmo assim algo lançar erro, o error boundary da T-018 contém o estrago na seção Projetos.
- **error-boundary**: o `LimiteDeErro` da T-018 continua lá, mas a T-019 tirou dele o papel de "solução" para a data inválida. *Por quê aqui:* o error boundary é a última rede de proteção. Se o card sabe lidar com o dado ruim, o usuário vê o card quase inteiro (só sem a data) em vez de uma seção vazia com aviso de erro.
- **bug-conhecido-com-it-fails-e-test-fail**: o BUG-2 estava registrado com `it.fails` em `github-cliente.spec.ts` e `CartaoDeProjeto.test.tsx`. *Por quê aqui:* quando a correção entrou, esses testes passaram a "falhar ao falhar", e isso obrigou a convertê-los em testes normais (critério de aceite). É o ciclo completo que começou na T-016: o bug vira teste antes de virar correção.
- **vi-mock-com-importoriginal-e-hoisting**: `vi.mock(caminho, fábrica)` troca um módulo inteiro por outro durante o teste. A fábrica recebe `importarOriginal`, que carrega o módulo de verdade, e assim dá para trocar só uma parte (aqui, o `default`, que é o componente). O Vitest **iça** (*hoisting*) o `vi.mock` para o topo do arquivo, antes dos `import`s, por isso a fábrica usa `await import(...)` em vez de variáveis do arquivo. *Por quê aqui:* os testes da T-018 precisavam de um card que lança erro, e a data inválida não serve mais para isso.
- **duble-de-teste-para-provocar-erro**: um *dublê* é uma peça falsa que substitui a verdadeira no teste. `comCartaoQueLancaErro` envolve o card verdadeiro e só lança erro para o título `TITULO_DO_CARTAO_QUE_LANCA_ERRO`; os outros projetos usam o card real. *Por quê aqui:* um teste apoiado num bug real fica acoplado a ele e quebra quando o bug é corrigido (o aviso do code-reviewer da T-018). Com um dublê, o erro é provocado de propósito e o teste continua provando a mesma coisa: um card que quebra não derruba a página.
- **controle-negativo-em-testes**: o dev viu os testes da T-018 ficarem vermelhos com a correção, o que provou que eles dependiam do bug. O qa rodou os testes novos contra o código da `main`: 10 testes de rota e 14 de 14 e2e falharam. *Por quê aqui:* um teste que nunca falhou não prova que a correção funciona.
- **tipos-de-teste-unitario-rota-e2e**: unitário (`ehDataEHoraIso` via `github-cliente.spec.ts`, com `it.each` para vários textos ruins; `CartaoDeProjeto.test.tsx` para o card sem data), rota (`/api/projetos` devolve `github: { disponivel: false }` para o projeto com data ruim e mantém os outros) e e2e (página real no celular e no desktop, sem erro no console, sem par `<dt>`/`<dd>` órfão na `<dl>`, sem rolagem horizontal em 360px).

## Onde aparece no projeto

- `apps/api/src/github/github-cliente.ts`: `traduzirResposta`, a regex `DATA_E_HORA_ISO` e a type guard `ehDataEHoraIso`.
- `apps/api/src/github/github-cliente.spec.ts`: o antigo `it.fails` do BUG-2 convertido e os cenários com `it.each`.
- `apps/web/src/componentes/CartaoDeProjeto/CartaoDeProjeto.tsx`: `UltimaAtualizacao` e `formatarData`.
- `apps/web/src/componentes/CartaoDeProjeto/CartaoDeProjeto.test.tsx`: card com data inválida não quebra e omite só a data.
- `apps/web/src/apoio-de-testes/cartao-que-lanca-erro.tsx`: o dublê `comCartaoQueLancaErro`.
- `apps/web/src/App.test.tsx` e `apps/web/src/componentes/Projetos/Projetos.test.tsx`: `vi.mock` do `CartaoDeProjeto` com `importarOriginal`.
- `apps/api/test/github.e2e-spec.ts`: bloco `GET /api/projetos com "pushed_at" que não é data e hora válida (T-019)`.
- `e2e/testes/projetos.spec.ts`: bloco `Projetos: data de atualização inválida (T-019)`.
