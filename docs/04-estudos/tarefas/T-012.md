# Diário de estudo — T-012

## O que foi feito

Esta foi a primeira tarefa em que **o front conversa com a API**. Até aqui, a seção Projetos não tinha conteúdo, e a API (T-010 e T-011) já respondia `GET /api/projetos` com os projetos curados e os dados vivos do GitHub. A T-012 ligou as duas pontas: quando a página abre, a seção Projetos pede a lista à API e mostra um **card** por projeto.

O caminho no front ficou em três camadas:

1. **Onde está a API** (`endereco-da-api.ts`): o endereço vem da variável de ambiente `VITE_API_URL`; sem ela, usa `http://localhost:3000` (a API local).
2. **Buscar** (`api/projetos.ts`): `buscarProjetos` chama o `fetch`, confere se a resposta deu certo e se é uma lista, e **rejeita a Promise em qualquer falha**, para quem chama tratar tudo num lugar só.
3. **Mostrar** (`useProjetos` + `Projetos` + `CartaoDeProjeto`): um hook guarda em que momento a busca está (**carregando**, **carregado** ou **erro**); a seção mostra o aviso certo ou a lista de cards. Cada card tem título, descrição, stacks, links (repositório e demo, em nova aba) e, se o GitHub respondeu, linguagem, estrelas e data da última atualização.

Dois requisitos guiaram o desenho: **RNF-03** (a API no Render gratuito pode levar ~1 minuto para "acordar"; só a seção Projetos espera, o resto da página aparece na hora) e a **falha amigável** (API fora do ar vira uma mensagem, não uma página quebrada).

A tarefa nasceu `eu-faco` (integração front ↔ API é o centro do aprendizado), mas o George passou as tarefas restantes para `agente-faz` em 2026-10-15; o aprendizado fica neste diário. O dev implementou com testes unitários (web com 74), o code-reviewer aprovou sem ajustes e o qa criou os e2e de sucesso, carregamento e falha (`e2e/testes/projetos.spec.ts`). Na verificação do encerramento, um e2e antigo ("carrega sem erros no console") ficou **instável**: sem API simulada, o navegador tentava `localhost:3000`, a conexão era recusada e aparecia um erro no console em algumas execuções. O George escolheu devolver ao qa (rodada 2), que passou a **simular a API em todos os e2e**. Resultado: 0 falhas em 1.680 execuções.

## Conceitos

- **fetch-nativo-e-tempo-limite**: o navegador já tem o `fetch`, o mesmo que a API usa no Node (T-011). A mesma armadilha vale aqui: o `fetch` **só rejeita em falha de rede**; um 500 da API chega como resposta "normal", por isso `buscarProjetos` confere `resposta.ok` e lança um erro se não for 200-299. Depois, `resposta.json()` entra como `unknown` e só passa se for lista (`Array.isArray`). *Por quê aqui:* sem essas duas conferências, um erro 500 ou um corpo estranho virariam um card quebrado em vez da mensagem amigável. Diferente da T-011, aqui **não há tempo limite próprio**: de propósito, porque a partida a frio pode levar um minuto e o aviso de carregamento já cobre a espera (o dev registrou isso como ponto para o George).
- **variaveis-de-ambiente-do-vite**: o Vite expõe variáveis em `import.meta.env`, mas **só as com prefixo `VITE_`**, e copia o valor para dentro do JavaScript no `npm run build`. Ou seja: **tudo que é `VITE_` é público**. *Por quê aqui:* o endereço da API muda por ambiente (local, Render) e não pode ficar escrito no código. Endereço pode ser público; segredo nunca (o token do GitHub fica só na API, RNF-05). O tipo da variável é declarado em `vite-env.d.ts`, o modelo fica em `apps/web/.env.example`, e a leitura é feita **a cada chamada** (não no topo do arquivo) para os testes poderem trocar o valor com `vi.stubEnv`. Detalhe: o endereço perde barras do final (`replace(/\/+$/, '')`) para não virar `...//api/projetos`.
- **custom-hook**: `useProjetos` é uma função que começa com `use` e usa outros hooks (`useState`, `useEffect`). Ela esconde *como* a busca acontece e devolve só o estado. *Por quê aqui:* o componente `Projetos` fica só com o "o que mostrar"; a lógica de busca, cancelamento e erro mora num lugar só e pode ser testada pela tela.
- **useeffect-com-limpeza-e-abortcontroller**: o `useEffect(..., [])` roda a busca uma vez, quando a seção aparece. A função que ele **devolve** é a **limpeza**: o React a chama quando o componente sai da tela, e ela chama `controlador.abort()`, que cancela a requisição. Antes de mudar o estado, o código confere `controlador.signal.aborted`, e um cancelamento nosso **não** vira mensagem de erro. *Por quê aqui:* sem isso, uma resposta chegando depois de o componente sumir tentaria atualizar algo que não existe. E no desenvolvimento o **StrictMode** monta, desmonta e monta de novo de propósito: a primeira busca é cancelada e só a segunda vale.
- **uniao-discriminada**: o estado é `{ situacao: 'carregando' } | { situacao: 'carregado'; projetos } | { situacao: 'erro' }`. O campo `situacao` é o discriminante. *Por quê aqui:* impede estados impossíveis (carregando **e** com erro ao mesmo tempo, comum com três `useState` booleanos separados) e só deixa ler `projetos` depois de conferir `situacao === 'carregado'`. O card usa a outra união, a da T-011: `if (!github?.disponivel) return null` e, depois disso, o TypeScript sabe que `estrelas` existe.
- **fallback-e-degradacao-graciosa**: a página tem três "planos B" em camadas. (1) API lenta: só a seção Projetos mostra "carregando" (o aviso fala da demora de até um minuto); o resto não espera (RNF-03). (2) API com erro: mensagem amigável no lugar dos cards. (3) GitHub indisponível para um projeto: o card aparece só com os dados curados. *Por quê aqui:* a API está num plano gratuito que dorme; o site não pode parecer quebrado por isso. **Ponto aberto** (code-reviewer e qa): uma data inválida em `ultimaAtualizacao` faz `Intl.DateTimeFormat.format` lançar `RangeError` e **apaga a página inteira**, porque não há **Error Boundary** (o componente do React que captura erros de renderização e mostra um plano B). Só acontece fora do contrato da API, mas mostra o limite do fallback atual.
- **regiao-viva-aria**: `<p role="status">` é uma **região viva**: quando o texto dentro dela muda, o leitor de tela anuncia a novidade sem mover o foco. Ela fica **sempre** na página, mesmo vazia, porque o leitor de tela só acompanha regiões que já existiam antes da mudança. Vazia, ela some do layout com `.aviso:empty { margin: 0 }`, e **não** com `display: none` (que a tiraria da árvore de acessibilidade). *Por quê aqui:* quem não enxerga a tela também precisa saber que os projetos estão carregando, que deu erro ou que a lista está vazia.
- **html-semantico-do-card**: cada card é um `<article>` (conteúdo que faz sentido sozinho) com `aria-labelledby` apontando para o próprio `<h3>`, então o leitor de tela anuncia "artigo Site de apresentação". Os dados vivos usam `<dl>`/`<dt>`/`<dd>` (pares rótulo: valor) e a data usa `<time dateTime="2026-10-01T12:00:00Z">`, que guarda a data original para máquinas enquanto a tela mostra a formatada. O id do título vem de `useId()`, que gera um id único por card. *Por quê aqui:* com vários cards, ids escritos à mão se repetiriam; e HTML com significado dá navegação melhor para leitores de tela e buscadores.
- **intl-formatacao-de-numero-e-data**: `new Intl.NumberFormat('pt-BR')` mostra `1234` como `1.234`; `new Intl.DateTimeFormat('pt-BR', { dateStyle: 'short' })` mostra a data como `01/10/2026`. O idioma vem de `conteudo.geral.localidade`, e os formatadores são criados **uma vez**, fora do componente. *Por quê aqui:* a API devolve números e datas "crus" (ISO 8601); formatar à mão é fácil de errar e não acompanharia uma troca de idioma.
- **key-em-listas-do-react**: ao desenhar uma lista com `map`, cada item precisa de uma `key` para o React saber qual item é qual entre uma renderização e outra. Aqui a `key` é `projeto.titulo`. *Por quê aqui:* o code-reviewer apontou (opcional) que dois projetos com o mesmo título repetiriam a `key`; uma chave estável e única (ex.: o endereço do repositório ou um id) evita bugs sutis de atualização.
- **css-grid-mobile-first**: a lista de cards é um `display: grid` com **uma coluna** por padrão (celular), **duas** a partir de `36rem` e **três** a partir de `60rem`, com `repeat(n, minmax(0, 1fr))` para colunas iguais que podem encolher (sem um texto longo forçar a largura). Dentro do card, `display: flex; flex-direction: column` e `margin-top: auto` nos links empurram os links para o pé do card. *Por quê aqui:* RNF-01 (responsivo, sem rolagem horizontal) e cards lado a lado alinhados embaixo mesmo com descrições de tamanhos diferentes.
- **simular-fronteira-externa-nos-testes**: nenhum teste chama a API de verdade. Nos **unitários**, o `fetch` do navegador é trocado por um dublê com `vi.stubGlobal('fetch', ...)`; por padrão (`configurar-testes.ts`) ele **nunca responde** (uma Promise que nunca resolve), que imita a partida a frio. `findBy*` da Testing Library espera o elemento aparecer, porque a resposta chega depois da primeira renderização. Nos **e2e**, `page.route('**/api/projetos', ...)` intercepta a requisição dentro do navegador e responde com `route.fulfill` (sucesso ou erro), `route.abort` (falha de rede) ou não responde (carregando). *Por quê aqui:* a API não sobe junto com os testes; e só simulando dá para reproduzir "API fora do ar" ou "90 s de partida a frio" sempre do mesmo jeito.
- **fixture-automatica-do-playwright**: o qa criou um `test` próprio em `e2e/apoio/teste.ts` com `test.extend` e uma fixture `{ auto: true }`, que roda **antes de todo teste** sem o teste pedir: ela registra a API "sem resposta". Quem precisa de cards registra a própria simulação, e como o Playwright tenta as rotas **da mais nova para a mais antiga**, a do teste vence. *Por quê aqui:* um passo esquecido em um arquivo de teste bastava para voltar o erro de conexão; com a fixture automática, a proteção vale para todos.
- **teste-instavel-flaky**: o e2e "carrega sem erros no console" passava às vezes e falhava às vezes: o erro `net::ERR_CONNECTION_REFUSED` aparecia em momentos diferentes a cada execução. A correção não foi afrouxar a checagem, e sim **remover a causa** (simular a API) e deixar o teste mais rigoroso (simula 4 projetos e só confere o console depois de os cards aparecerem). A primeira ideia, "lista vazia" como padrão, também falhou: 1 vez em 1.680 a seção Projetos **encolhia no meio de uma rolagem suave** e tirava as seções de baixo do lugar; por isso o padrão ficou "sem resposta" (a seção não muda de tamanho). Para provar a estabilidade, o qa rodou `--repeat-each=10` e um **servidor espião** na porta 3000, que confirmou que nenhuma requisição chegava à API real. *Por quê aqui:* teste instável é pior que teste nenhum: ensina a ignorar falhas.
- **cors**: o navegador só deixa uma página de uma origem (ex.: `localhost:5173`) ler a resposta de outra origem (ex.: `localhost:3000`) se a API disser que permite, pelos cabeçalhos de CORS. A API ainda **não tem CORS**: localmente, o front real não consegue chamar a API real. Os e2e não pegam isso, porque **respostas simuladas pelo Playwright não passam pela checagem de CORS**. *Por quê aqui:* é o RNF-05 (a API aceita só a origem do front publicado) e ficou para a T-013, que também precisa aceitar a origem de desenvolvimento.

## Onde aparece no projeto

- `apps/web/src/api/endereco-da-api.ts`: `VITE_API_URL`, padrão `http://localhost:3000`, remoção da barra final.
- `apps/web/src/api/projetos.ts`: `buscarProjetos` com `fetch`, `resposta.ok`, `Array.isArray` e o `signal` de cancelamento.
- `apps/web/src/vite-env.d.ts` e `apps/web/.env.example`: tipo e modelo da variável de ambiente.
- `apps/web/src/componentes/Projetos/useProjetos.ts`: custom hook, união `EstadoDosProjetos`, `useEffect` com limpeza e `AbortController`.
- `apps/web/src/componentes/Projetos/Projetos.tsx`: região viva `role="status"`, lista com `aria-labelledby` e `key`.
- `apps/web/src/componentes/Projetos/Projetos.module.css`: grid mobile-first (1/2/3 colunas) e `.aviso:empty`.
- `apps/web/src/componentes/CartaoDeProjeto/CartaoDeProjeto.tsx`: `<article>`, `useId`, `<dl>`, `<time dateTime>`, `Intl.NumberFormat`/`Intl.DateTimeFormat` e links só quando existem.
- `apps/web/src/componentes/CartaoDeProjeto/CartaoDeProjeto.module.css`: card em coluna flex e `margin-top: auto` nos links.
- `apps/web/src/configurar-testes.ts`: `fetch` padrão que nunca responde nos unitários.
- `apps/web/src/api/*.test.ts`, `apps/web/src/componentes/Projetos/Projetos.test.tsx`, `apps/web/src/App.test.tsx`: `vi.stubGlobal`, `vi.stubEnv`, `findBy*` e o teste de que o resto da página não espera a API.
- `apps/web/src/conteudo/pt-BR.ts`: textos do bloco `projetos` (carregando, erro, vazio, rótulos) e `geral.localidade` (RF-09).
- `e2e/apoio/api.ts`: `simularApi`, `simularApiSemResposta`, `responder` e `PROJETOS_DE_EXEMPLO`.
- `e2e/apoio/teste.ts`: o `test` com a fixture automática.
- `e2e/testes/projetos.spec.ts`: e2e de sucesso, carregamento (inclusive partida a frio), falhas, lista vazia, colunas, teclado e região viva.
- `apps/api/src/criar-app.ts`: onde o CORS vai entrar (T-013).

## Exercícios

1. **Ver os três estados na prática:** suba o front (`npm run dev -w apps/web`) **sem** a API e abra a seção Projetos: que aviso aparece e quanto tempo ele fica? Agora suba também a API (`npm run dev -w apps/api`) e recarregue: os cards aparecem? Se não, abra o console do navegador e leia o erro (dica: conceito `cors`). Responda: por que os e2e passaram mesmo com esse problema? Por fim, pare a API com a página aberta e recarregue: qual estado aparece, e por que o resto da página continua normal?
2. **Estado com booleanos x união discriminada:** reescreva `useProjetos` num rascunho (não no projeto) com três `useState` separados: `carregando`, `erro` e `projetos`. Liste quais combinações impossíveis passam a existir (ex.: `carregando = true` e `erro = true`) e em que ordem você teria de chamar os três `set...` para nunca mostrar uma delas. Depois compare com o tipo `EstadoDosProjetos`: o que o TypeScript passa a garantir sozinho? Bônus: tire o `if (!controlador.signal.aborted)` do tratamento de erro e pense no que o StrictMode mostraria no desenvolvimento.
