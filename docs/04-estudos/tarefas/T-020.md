# Diário de estudo — T-020

## O que foi feito

A tarefa corrigiu o BUG-3, achado no pente-fino de testes da T-016. A seção Projetos desenha um card por projeto com `<li key={projeto.titulo}>`: o **título** é a `key` que o React usa para saber qual card é qual. Só que nada impedia dois projetos com o mesmo título no arquivo curado (`apps/api/conteudo/projetos.json`). Com dois títulos iguais, o React avisa "Encountered two children with the same key" e, quando a lista muda, pode trocar ou repetir cards.

Havia dois lugares possíveis para corrigir: no front (usar outra `key`) ou na API (não deixar o título repetido chegar ao front). O George decidiu **corrigir na API**:

1. **A validação do arquivo curado recusa títulos repetidos.** Em `validar-projetos-curados.ts`, a função nova `problemasDeTitulosRepetidos` percorre os projetos e, para cada título que repete o de um projeto anterior, gera uma linha de erro como `projeto 3 ("meu projeto"): título repetido — o mesmo do projeto 2 ("Meu projeto"); cada projeto precisa de um título único`. Essa linha entra na **mesma lista** dos outros problemas (campo faltando, endereço inválido etc.), e o arquivo inteiro é recusado de uma vez.
2. **A API nem sobe com o arquivo inválido.** O arquivo curado é lido e validado na inicialização (desde a T-010). Com título repetido, a API para com uma mensagem que diz o arquivo e os projetos envolvidos, em vez de subir e entregar dados ruins ao front.
3. **O front ficou como estava.** Ele continua usando o título como `key`. O `it.fails` do BUG-3 em `Projetos.test.tsx` também ficou: só o comentário mudou, explicando que o front confia no contrato da API (segunda decisão do George, opção A).

A comparação é um pouco mais esperta que "textos idênticos": ela ignora espaços nas pontas, espaços a mais no meio e maiúsculas/minúsculas. "Site" e "  SITE " contam como repetidos, porque para o visitante seriam dois cards com o mesmo nome. Acento e hífen continuam fazendo diferença ("apresentação" e "apresentacao" são títulos diferentes).

Nos testes: o dev escreveu 9 testes unitários da validação e 1 de leitura de arquivo; o qa escreveu 5 cenários de rota (7 testes, a API subindo ou não com arquivos de verdade numa pasta temporária) e 1 e2e com o conteúdo curado real. Com o validador antigo, 5 dos 7 testes de rota falham.

## Conceitos

- **chave-key-no-react**: ao desenhar uma lista, o React usa a `key` de cada item para casar o item novo com o antigo entre uma renderização e outra. *Por quê aqui:* se duas chaves são iguais, o React não consegue distinguir os dois cards, avisa no console e pode reaproveitar o card errado. O título funciona como `key` só se for único, e esta tarefa garante isso na origem dos dados.
- **validacao-em-tempo-de-execucao-com-type-guards**: o JSON lido do disco entra como `unknown` e só sai como `ProjetoCurado[]` depois de conferido. `ehObjeto` e `ehTextoNaoVazio` são *type guards*: quando devolvem `true`, o TypeScript passa a confiar no tipo. *Por quê aqui:* `problemasDeTitulosRepetidos` só pode ler `item.titulo` como texto depois de `ehObjeto(item) && ehTextoNaoVazio(item.titulo)`. Itens sem título válido ficam de fora da comparação, porque o erro deles já é o do campo `"titulo"` (assim o mesmo problema não aparece duas vezes).
- **normalizacao-de-texto-para-comparacao**: normalizar é transformar o texto numa forma padrão antes de comparar. `tituloParaComparar` faz `trim()` (tira espaços das pontas), `replace(/\s+/g, ' ')` (junta espaços seguidos num só, como o navegador faz na tela) e `toLocaleLowerCase('pt-BR')` (tudo minúsculo, com as regras do português). *Por quê aqui:* a pergunta certa não é "os textos são idênticos?", e sim "o visitante veria dois cards com o mesmo nome?". O título original é mantido para exibir e para a mensagem de erro; a forma normalizada serve só para comparar.
- **map-para-achar-duplicatas**: um `Map` guarda pares chave → valor e responde `get(chave)` rápido. `primeiroComOTitulo` usa o título normalizado como chave e guarda o número e o título do **primeiro** projeto que o usou. *Por quê aqui:* numa única passada pela lista dá para saber se o título já apareceu e, se sim, citar na mensagem qual projeto veio antes. Comparar cada projeto com todos os outros (dois laços) também funcionaria, mas seria mais lento e geraria a mesma repetição várias vezes. Com três títulos iguais, os dois últimos apontam para o primeiro.
- **provider-de-fabrica-e-fail-fast**: *fail fast* (falhar cedo) é parar logo, com erro claro, em vez de seguir com dado ruim. O arquivo curado é lido por um provider de fábrica do NestJS na inicialização, então um erro de validação impede a API de subir. *Por quê aqui:* quem edita o `projetos.json` descobre o título repetido na hora em que a API sobe (no próprio computador ou no deploy), com a mensagem apontando os projetos, e não depois, olhando cards trocados no site publicado.
- **contrato-entre-front-e-api**: contrato é o que um lado promete ao outro sobre os dados. A partir desta tarefa, a API promete "não há dois projetos com o mesmo título", e o front se apoia nisso ao usar o título como `key`. *Por quê aqui:* a regra fica num lugar só (a validação), documentada no `apps/api/conteudo/README.md` e coberta por testes dos dois lados. O lado fraco, registrado no `it.fails`: se outra fonte de dados quebrar o contrato, o front volta a ter o problema. Foi uma escolha consciente do George (opções avaliadas: manter o `it.fails`, mudar também a `key` no front ou apagar o `it.fails`).
- **bug-conhecido-com-it-fails-e-test-fail**: `it.fails` é um teste que **precisa falhar** para ficar verde; se um dia passar, a suíte avisa. *Por quê aqui:* diferente da T-019, o `it.fails` do BUG-3 não virou teste normal, porque o front não mudou: com dois títulos iguais ele ainda avisa sobre chave duplicada. O teste continua documentando esse comportamento, e o comentário agora explica que a proteção está na API.
- **testes-com-testing-module-e-override-provider**: nos testes de rota, `Test.createTestingModule(...).overrideProvider(PROJETOS_CURADOS)` monta a API trocando o provider do arquivo curado por um que lê um arquivo temporário (`mkdtempSync` numa pasta do sistema). *Por quê aqui:* para provar que a API **não sobe** com título repetido, o teste precisa tentar subir a API de verdade com um arquivo ruim. A função `erroAoSubirCom` devolve a mensagem do erro e falha o teste se a API subir.
- **controle-negativo-em-testes**: o qa rodou os testes novos contra o validador da `main` e 5 dos 7 falharam, prova de que eles detectam o bug. Os 2 que passaram são de propósito: protegem contra **rigor excessivo**. Um confere que títulos parecidos mas diferentes ("Site de apresentação", "Site de apresentação 2", "Site de apresentacao", "Site-de-apresentação") sobem normalmente; o outro confere que o `projetos.json` real é válido. *Por quê aqui:* uma validação rígida demais também é bug, porque recusaria conteúdo legítimo.
- **tipos-de-teste-unitario-rota-e2e**: unitário (`validar-projetos-curados.spec.ts`: a função sozinha, com vários casos de repetição), leitura de arquivo (`ler-projetos-curados.spec.ts`), rota (`apps/api/test/projetos.e2e-spec.ts`: a API inteira subindo ou não) e e2e (`e2e/testes/projetos.spec.ts`: o navegador desenha um `<h3>` por projeto do arquivo curado real, sem títulos repetidos e sem erro no console).

## Onde aparece no projeto

- `apps/api/src/projetos/validar-projetos-curados.ts`: `validarProjetosCurados` (junta todos os problemas), `problemasDeTitulosRepetidos` (o `Map`) e `tituloParaComparar` (a normalização).
- `apps/api/src/projetos/validar-projetos-curados.spec.ts`: os testes unitários da regra nova.
- `apps/api/src/projetos/ler-projetos-curados.spec.ts`: a leitura de um arquivo com título repetido.
- `apps/api/conteudo/README.md`: a regra "cada projeto precisa de um título único", com exemplo da mensagem de erro.
- `apps/api/test/projetos.e2e-spec.ts`: bloco `arquivo curado com títulos repetidos (T-020)`, com `erroAoSubirCom` e o `it.each` dos três casos (idêntico, com espaços, outra caixa).
- `e2e/testes/projetos.spec.ts`: bloco `Projetos: títulos únicos com o conteúdo curado de verdade (T-020)`.
- `apps/web/src/componentes/Projetos/Projetos.tsx`: a `key={projeto.titulo}` que motivou a tarefa.
- `apps/web/src/componentes/Projetos/Projetos.test.tsx`: o `it.fails` do BUG-3, com o comentário que aponta para a validação na API.
