# Diário de estudo — T-010

## O que foi feito

Até aqui a API só tinha o `GET /api/health` (T-005). A T-010 criou o **primeiro módulo de domínio** da API, o `projetos`, e a primeira rota que devolve conteúdo de verdade: **`GET /api/projetos`**.

O caminho da informação é este:

1. O George escreve os projetos que quer mostrar, na ordem que quer, num **arquivo curado** em JSON: `apps/api/conteudo/projetos.json` (por enquanto com 2 projetos de exemplo, que ele vai trocar pelos reais). O formato está documentado ao lado, em `apps/api/conteudo/README.md`.
2. Quando a API **sobe**, ela lê esse arquivo **uma vez** e confere campo a campo se ele segue o formato do tipo `Projeto` de `packages/shared`.
3. Se o arquivo estiver ausente, não for JSON ou tiver algum campo errado, a API **nem sobe**: o log mostra o caminho do arquivo e **todos** os problemas de uma vez (ex.: `projeto 2 ("Meu projeto"): campo "stacks" é obrigatório...`).
4. Se estiver certo, cada `GET /api/projetos` devolve a lista, em JSON, na ordem do arquivo.

Foi uma tarefa `agente-faz`, feita para servir de **exemplo de módulo, controller e service** no NestJS: o dev implementou com 29 testes unitários, o code-reviewer aprovou (com três opcionais: um `projetos.module.spec.ts` próprio, restringir o campo `imagem` a caminho ou `http(s)` e apagar o antigo `compartilhamento.spec.ts`) e o qa escreveu 19 testes de rota com Supertest. A escolha de JSON numa pasta `conteudo/` foi do dev, sem ADR: o RF-06 só pede "um arquivo curado no repositório", então o revisor tratou como detalhe de implementação, não como decisão do George.

## Conceitos

- **nestjs-modulos-controllers-e-bootstrap**: o módulo agora tem as três peças. O `ProjetosController` só traduz HTTP para chamadas do service (`@Get()` → `listar()`); o `ProjetosService` guarda a regra do domínio; o `ProjetosModule` junta os dois e é importado no `AppModule`. *Por quê aqui:* a T-011 vai juntar os dados vivos do GitHub à lista; essa regra entra no service sem tocar no controller, e o controller continua testável sozinho.
- **injecao-de-dependencia-no-nestjs**: ninguém faz `new ProjetosService()` no código da API; o Nest cria as instâncias e as **entrega** a quem pede no construtor. Há dois jeitos de pedir: **por tipo** (o controller declara `private readonly projetosService: ProjetosService` e o Nest entende pela classe) e **por token** (o service declara `@Inject(PROJETOS_CURADOS) private readonly projetos: Projeto[]`). *Por quê aqui:* `Projeto[]` não é uma classe, então não serve de "nome" para o Nest procurar; por isso existe o token `PROJETOS_CURADOS = Symbol('PROJETOS_CURADOS')`, num arquivo só dele para o módulo e o service importarem sem depender um do outro. Um `Symbol` é sempre único, então não colide com outro token de mesmo texto.
- **provider-de-fabrica-e-fail-fast**: no módulo, o provider `{ provide: PROJETOS_CURADOS, useFactory: () => lerProjetosCurados() }` diz ao Nest "para entregar este token, chame esta função". O Nest chama a fábrica **uma vez, ao montar a aplicação**. *Por quê aqui:* é o que faz o critério "arquivo inválido gera erro na inicialização, não em tempo de requisição". Isso é **fail fast** (falhar cedo): um arquivo quebrado aparece no deploy, no log de subida, e não semanas depois, quando um visitante abre a seção de projetos e recebe um erro 500.
- **validacao-em-tempo-de-execucao-com-type-guards**: o TypeScript só confere tipos no código; um JSON lido do disco pode conter qualquer coisa. Por isso `JSON.parse` entra como `unknown` (o tipo que obriga a conferir antes de usar) e só sai como `Projeto[]` depois de `validarProjetosCurados`. As funções `ehObjeto`, `ehTextoNaoVazio` e `ehListaDeTextos` são **type guards** (`valor is string`): quando devolvem `true`, o TypeScript passa a tratar o valor com aquele tipo. *Por quê aqui:* sem isso, um `"stacks": "React"` (texto em vez de lista) passaria e quebraria o card no front. A validação também recusa **campos desconhecidos** (pega `"titlo"` digitado errado), aceita só `http(s)` em `repositorio` e `demo` e junta todos os problemas numa mensagem só. Foi escrita à mão, sem biblioteca nova (Zod, class-validator), porque a stack da ADR-0001 não tem uma.
- **caminho-relativo-com-import-meta-url**: `fileURLToPath(new URL('../../conteudo/projetos.json', import.meta.url))` calcula o caminho do arquivo a partir **do próprio arquivo de código**, e não da pasta de onde o comando foi rodado (`process.cwd()`). *Por quê aqui:* a API roda de jeitos diferentes (`npm run dev` em `src/`, `node dist/main.js` depois do build, testes na raiz do monorepo); subir duas pastas leva a `apps/api/` tanto de `src/projetos/` quanto de `dist/projetos/`. O revisor conferiu que o caminho funciona também no `dist/`.
- **copia-defensiva-com-structuredclone**: `listar()` devolve `structuredClone(this.projetos)`, uma **cópia profunda** da lista. *Por quê aqui:* a lista é lida uma vez e guardada no service; se alguém alterasse o resultado (um `pop()`, um `push` nas `stacks`), a próxima requisição receberia a lista estragada. O teste `devolve uma cópia` do service e o teste de rota `respostas seguidas são iguais` protegem isso.
- **testes-com-testing-module-e-override-provider**: `Test.createTestingModule({ imports: [ProjetosModule] }).compile()` monta o módulo de verdade, com a injeção funcionando, sem subir servidor. `.overrideProvider(PROJETOS_CURADOS).useFactory({ factory: () => lerProjetosCurados(caminhoTemporario) })` troca **só** a fonte dos dados, apontando para um arquivo criado com `mkdtempSync` numa pasta temporária. *Por quê aqui:* dá para testar arquivo inválido sem estragar o `projetos.json` real, e o resto do módulo continua sendo o de produção. `lerProjetosCurados(caminho)` recebe o caminho como parâmetro (com o arquivo curado como padrão) justamente para permitir isso.
- **tipos-de-teste-unitario-rota-e2e**: o **dev** testou peças isoladas (validação, leitura, service, controller com `new`, montagem do módulo). O **qa** testou a **rota** com Supertest, fazendo requisições HTTP de verdade na API montada em memória: resposta igual ao JSON cru do arquivo e na mesma ordem, `content-type` JSON, prefixo `/api` obrigatório, `POST`/`PUT`/`DELETE` dão 404 e oito casos de arquivo inválido com `it.each`. *Por quê aqui:* um teste prova que o arquivo é lido **na subida**: ele estraga o arquivo **depois** de a API subir e confere que a resposta não muda. Para os casos de subida, o teste monta a app com `createNestApplication` e repete `setGlobalPrefix`, porque o `criarApp` não permite trocar o provider.

## Onde aparece no projeto

- `apps/api/conteudo/projetos.json`: o arquivo curado (2 projetos de exemplo).
- `apps/api/conteudo/README.md`: formato dos campos e exemplo de erro de arquivo inválido.
- `apps/api/src/projetos/projetos.module.ts`: controller, service e o provider de fábrica `PROJETOS_CURADOS`.
- `apps/api/src/projetos/projetos.controller.ts`: `@Controller('projetos')` e `@Get()`, injeção por tipo.
- `apps/api/src/projetos/projetos.service.ts`: `@Inject(PROJETOS_CURADOS)` e `structuredClone`.
- `apps/api/src/projetos/projetos-curados.token.ts`: o `Symbol` usado como token.
- `apps/api/src/projetos/ler-projetos-curados.ts`: `CAMINHO_DO_ARQUIVO_CURADO` com `import.meta.url` e os três erros possíveis (leitura, JSON, formato).
- `apps/api/src/projetos/validar-projetos-curados.ts`: `ArquivoDeProjetosInvalidoError`, os type guards e a lista de campos conhecidos.
- `apps/api/src/projetos/*.spec.ts`: testes unitários do dev (em `projetos.controller.spec.ts` também os do módulo, com `overrideProvider`).
- `apps/api/src/app.module.ts`: `imports: [HealthModule, ProjetosModule]`.
- `apps/api/test/projetos.e2e-spec.ts`: os testes de rota do qa (Supertest).
- `packages/shared/src/projeto.ts`: o tipo `Projeto` que a resposta segue.

## Exercícios

Rode `npm test -w apps/api` e depois `npm run dev -w apps/api`. Quantos problemas a mensagem lista? Em que momento a API falha: ao subir ou ao chamar `/api/projetos`? Que linha de `projetos.module.ts` explica isso? Desfaça as mudanças no fim.
2. **Injeção por token na prática:** no `projetos.service.ts`, apague o `@Inject(PROJETOS_CURADOS)` e rode os testes. Depois responda: por que o teste `responde com a lista do service` (que usa `new`) continua passando mesmo assim?
