# Diário de estudo — T-021

## O que foi feito

A tarefa corrigiu o BUG-4, achado no pente-fino de testes da T-016. O problema: se alguém abrisse o `apps/api/conteudo/projetos.json` num editor do Windows e salvasse como "UTF-8 com BOM", **a API não subia mais**. A mensagem dizia que o arquivo "não é um JSON válido", mesmo com o conteúdo visivelmente certo.

O motivo é uma marca invisível. Alguns editores gravam três bytes extras no começo do arquivo (`EF BB BF`), o **BOM**. O Node lê esses bytes como um caractere, o U+FEFF, e o `readFileSync(caminho, 'utf8')` **não o remove**: o texto lido começa com `﻿[` em vez de `[`. O `JSON.parse` não aceita esse caractere antes do JSON e lança erro.

A correção é pequena e fica em `apps/api/src/projetos/ler-projetos-curados.ts`:

1. Uma função nova, `removerBomInicial`, tira **um único** U+FEFF do **início** do texto, se houver: `texto.startsWith(BOM) ? texto.slice(BOM.length) : texto`.
2. Ela roda dentro do mesmo `try` do `JSON.parse`. Assim, se o resto do arquivo estiver errado, o erro continua sendo "não é um JSON válido" e continua trazendo o caminho do arquivo.
3. O dev **não** usou `trim()` de propósito: o `trim()` também apaga U+FEFF e espaços, e isso mexeria em conteúdo legítimo ou esconderia arquivos realmente quebrados.
4. O `apps/api/conteudo/README.md` agora diz que o arquivo pode ser salvo em UTF-8, com ou sem BOM.

O `it.fails` do BUG-4 em `ler-projetos-curados.spec.ts` virou teste normal (com a mesma asserção), e o dev somou 7 cenários unitários. O qa acrescentou 5 cenários de rota em `apps/api/test/projetos.e2e-spec.ts`, gravando os bytes `EF BB BF` de verdade no disco e subindo a API inteira. Com o código antigo, 4 dos 5 cenários de rota falham; com uma correção ampla demais (`trimStart()`), o cenário dos "dois BOMs" falha.

## Conceitos

- **bom-e-codificacao-utf-8**: UTF-8 é a forma de gravar texto como bytes. O BOM (*byte order mark*, marca de ordem dos bytes) nasceu para indicar a ordem dos bytes no UTF-16; no UTF-8 ele não é necessário, mas alguns editores do Windows o gravam mesmo assim, como uma "assinatura" de que o arquivo é UTF-8. *Por quê aqui:* o arquivo curado é editado à mão pelo George; o projeto não controla qual editor ele usa, então a API precisa aceitar as duas formas de salvar.
- **bytes-versus-caracteres-no-node**: no disco o BOM são 3 bytes (`EF BB BF`); depois de decodificado ele vira 1 caractere (U+FEFF). `readFileSync(caminho)` sem codificação devolve um `Buffer` (bytes crus); com `'utf8'` devolve uma string (caracteres) e mantém o BOM como primeiro caractere. *Por quê aqui:* o código da API trabalha com a string (por isso compara com `'﻿'`), e o teste de rota trabalha com bytes (`Buffer.from([0xef, 0xbb, 0xbf])`) para gravar o arquivo exatamente como um editor gravaria. O teste ainda confere `readFileSync(arquivo).subarray(0, 3)` para provar que os bytes estão lá.
- **trim-e-espacos-unicode**: para o JavaScript, U+FEFF conta como espaço, então `trim()`, `trimStart()` e `trimEnd()` também o removem, junto com espaços, tabs e quebras de linha. *Por quê aqui:* um `trim()` resolveria o bug, mas faria mais do que o pedido: removeria qualquer quantidade de BOMs e espaços, aceitando arquivos que deveriam ser recusados (como o de dois BOMs seguidos). A correção certa mexe só no que o editor grava.
- **remover-so-o-prefixo-com-startswith-e-slice**: `startsWith(BOM)` pergunta se o texto começa com a marca; `slice(BOM.length)` devolve o texto a partir do primeiro caractere depois dela. *Por quê aqui:* garante que só **um** BOM e só no **início** sai. Um U+FEFF no meio de um título ou descrição é conteúdo do projeto e é preservado (há teste unitário para isso), e dois BOMs no início continuam sendo um arquivo inválido.
- **escapes-unicode-em-strings-js**: `'﻿'` escreve o caractere pelo seu código, sem precisar colar um caractere invisível no código-fonte. Os testes unitários usam outra forma equivalente, `String.fromCharCode(0xfeff)`. *Por quê aqui:* um caractere invisível colado no arquivo seria impossível de enxergar na revisão; o escape deixa explícito o que está sendo comparado.
- **provider-de-fabrica-e-fail-fast**: o arquivo curado é lido por um provider de fábrica do NestJS na inicialização, então qualquer erro de leitura impede a API de subir. *Por quê aqui:* foi por isso que o BOM derrubava a API inteira (e não só a rota de projetos). A correção mantém o *fail fast* para arquivos realmente inválidos: os cenários de "só BOM", "BOM + espaços", "BOM + JSON quebrado" e "dois BOMs" continuam impedindo a subida, com o caminho do arquivo na mensagem.
- **bug-conhecido-com-it-fails-e-test-fail**: o `it.fails` documentava o BUG-4 como "comportamento errado conhecido": ele precisava falhar para ficar verde. *Por quê aqui:* com a correção, o teste passou a passar e, portanto, o `it.fails` ficaria vermelho. Trocá-lo por `it` com a **mesma asserção** é o sinal de que o bug foi corrigido (diferente da T-020, em que o `it.fails` do BUG-3 ficou porque o front não mudou).
- **testes-com-testing-module-e-override-provider**: nos testes de rota, `criarAppComArquivo(caminho)` monta a API trocando o provider do arquivo curado por um que lê um arquivo temporário (`mkdtempSync` numa pasta do sistema, apagada no `afterEach`). *Por quê aqui:* para provar que "a API sobe", o teste precisa subir a API de verdade com um arquivo com BOM e chamar `GET /api/projetos`.
- **controle-negativo-em-testes**: o qa rodou os testes novos em duas versões "erradas" do código. Contra o código da `main` (sem correção), os cenários de BOM válido falharam: prova de que pegam o bug. Contra uma correção **ampla demais** (`trimStart()`), o cenário dos dois BOMs falhou: prova de que pegam o excesso. *Por quê aqui:* um teste que passa com qualquer código não protege nada; os dois controles mostram que os testes distinguem a correção certa das erradas.
- **tipos-de-teste-unitario-rota-e2e**: unitário em `ler-projetos-curados.spec.ts` (a função sozinha, lendo arquivos temporários) e rota em `apps/api/test/projetos.e2e-spec.ts` (a API inteira subindo ou não). Não houve e2e novo no navegador: a interface não mudou, e o cenário de rota 3 já cobre o `projetos.json` real regravado com BOM. Outro detalhe do qa: em vez de fixar a resposta esperada, ele **compara** a resposta do arquivo com BOM com a do mesmo arquivo sem BOM, o que testa exatamente o critério "funciona igual".

## Onde aparece no projeto

- `apps/api/src/projetos/ler-projetos-curados.ts`: a constante `BOM = '﻿'`, a função `removerBomInicial` e a chamada `JSON.parse(removerBomInicial(texto))` dentro de `lerProjetosCurados`.
- `apps/api/src/projetos/ler-projetos-curados.spec.ts`: bloco `arquivo salvo em UTF-8 com BOM (T-021)`, com o antigo `it.fails` virado `it` ("lê um arquivo salvo em UTF-8 com BOM"), o U+FEFF interno preservado e o caso dos dois BOMs.
- `apps/api/test/projetos.e2e-spec.ts`: bloco `arquivo curado salvo em UTF-8 com BOM (T-021)`, com `gravarComBom` (bytes crus no disco), a comparação com e sem BOM e o `it.each` dos arquivos que não devem subir.
- `apps/api/conteudo/README.md`: a orientação "Salve o arquivo em UTF-8, com ou sem BOM".
