# Diário de estudo — T-017

## O que foi feito

O sintoma era "não está compilando, não tem o module": num clone novo, o VS Code, o `npm run dev` (o `nest start` compila antes de subir a API) e o `tsc` de cada app davam `Cannot find module '@site-apresentacao/shared'`.

A causa: desde a T-005, o `packages/shared/package.json` dizia que os tipos do pacote estavam em `./dist/index.d.ts`. Só que a pasta `dist/` é **gerada pelo build** e fica fora do git. Sem rodar `npm run build` antes, o arquivo não existia e o TypeScript não achava o pacote. Só o `npm run build` da raiz funcionava, porque ele compila o shared primeiro.

A correção (decisão do George, Q1-A): o campo `types` passou a apontar para o **código-fonte**, `./src/index.ts`. Isso só funciona porque o pacote **só exporta tipos** e todo mundo o importa com `import type`: os tipos somem quando o código vira JavaScript, então ninguém precisa da `dist/` para rodar.

Além da troca de uma linha, o dev escreveu 5 testes em `packages/shared/test/pacote.test.ts`. Eles usam o compilador do TypeScript como biblioteca e "fingem" que a `dist/` existe ou não, sem apagar nada do disco. O último teste protege a regra que sustenta tudo: nenhum arquivo de `packages/shared/src/` pode exportar um valor (`const`, `function`, `class`...). O devops atualizou o `README.md`, que ainda mandava compilar o shared antes de tudo. O qa provou os critérios numa **cópia limpa** do repositório, sem `dist/`, montada no scratchpad.

## Conceitos

- **resolucao-de-modulos-do-typescript**: o caminho que o TypeScript percorre para transformar `'@site-apresentacao/shared'` num arquivo de verdade. Primeiro acha a pasta (pelo link do workspace em `node_modules/`), depois lê o `package.json` dela para saber qual arquivo abrir. A API usa `moduleResolution: nodenext` (regras do Node) e o front usa `bundler` (regras do Vite); os dois respeitam o campo `exports`. *Por quê aqui:* o erro estava no segundo passo: a pasta era encontrada, mas o arquivo indicado (`dist/index.d.ts`) não existia. O `--traceResolution` do `tsc` mostra esse caminho passo a passo, e foi como a revisão confirmou a correção.
- **exports-e-condicao-types**: o campo `exports` do `package.json` diz o que o pacote oferece; dentro dele, cada **condição** aponta um arquivo para um tipo de consumidor. `types` é lido pelo TypeScript na hora de checar tipos; `default` é o JavaScript que o Node ou o Vite carregaria ao rodar. *Por quê aqui:* dá para separar os dois. Os tipos vêm de `./src/index.ts` (sempre existe, está no git), e o `default` continua em `./dist/index.js`, que nunca é carregado de fato.
- **import-type-e-apagamento-de-tipos**: `import type { Projeto } from '...'` avisa ao compilador que só o **tipo** é usado. Ao gerar o JavaScript, esse import é apagado por inteiro (*type erasure*). *Por quê aqui:* é a condição para apontar os tipos para o fonte. Como o JavaScript compilado da API e do front nem menciona o shared (o qa conferiu), nada em tempo de execução precisa da `dist/`. Se alguém um dia exportar um valor do shared, essa garantia cai, e por isso existe o teste 5.
- **monorepo-com-npm-workspaces**: o `npm install` cria o link `node_modules/@site-apresentacao/shared` → `packages/shared`. *Por quê aqui:* o link resolve **onde** está o pacote; a T-017 respondeu a outra metade da pergunta da T-005, **como** o TypeScript lê os arquivos dele: agora pelo código-fonte, sem build. Efeito bom extra: uma mudança em `packages/shared/src` vale na hora, mesmo com uma `dist/` velha no disco.
- **api-do-compilador-typescript**: o pacote `typescript` não é só o comando `tsc`; ele pode ser usado como biblioteca. `ts.resolveModuleName` pergunta "para onde vai este import?"; `ts.createProgram` + `ts.getPreEmitDiagnostics` checam um programa inteiro e devolvem os erros; um **compiler host** é o objeto pelo qual o compilador lê o disco (`fileExists`, `readFile`, `directoryExists`). *Por quê aqui:* trocando o host, o teste esconde ou simula a `dist/` sem apagar a pasta real (apagar era negado por permissão e mudaria o checkout de quem roda o teste). O arquivo que usa o tipo também só existe na memória.
- **controle-negativo-em-testes**: rodar o teste contra a versão **errada** para ver se ele falha. *Por quê aqui:* um teste que passa sempre não protege nada. O dev e o qa voltaram o `types` antigo (4 dos 5 testes falharam) e colocaram um export de valor no shared (o teste 5 falhou). O próprio teste 5 faz isso por dentro: antes de olhar o código real, prova que a função reconhece `export const versao = 1`. E o `@ts-expect-error` no código de exemplo é outro controle: se o tipo `Projeto` virasse `any`, o erro esperado não aconteceria e o TypeScript reclamaria.
- **tsconfig-separado-para-testes**: um segundo arquivo, `packages/shared/tsconfig.test.json`, só para **checar os tipos** dos testes (`noEmit: true`, `types: ["node"]`). *Por quê aqui:* o pacote em si não depende de ambiente nenhum (`types: []`) e só `src/` vai para a `dist/`. Os testes rodam no Node e usam `node:fs`, então precisam dos tipos do Node (`@types/node` entrou como devDependency), mas não podem ser compilados junto com o pacote. O `build` do shared roda os dois: `tsc && tsc -p tsconfig.test.json`.
- **verificar-antes-de-concluir**: provar o critério no cenário que ele descreve, não num parecido. *Por quê aqui:* o checkout de trabalho sempre tinha uma `dist/` antiga, que escondia o problema. O qa montou uma cópia só com os arquivos rastreados pelo git (`git ls-files` + `git show`), rodou `npm ci` e testou tudo lá (dev, build, testes, e2e). Ele também apontou (opcional) que no CI o build roda antes dos testes, então a `dist/` sempre existe; um `tsc --noEmit` antes do build provaria o "clone sem dist" no próprio CI.

## Onde aparece no projeto

- `packages/shared/package.json`: `exports["."].types` → `./src/index.ts`; `default` → `./dist/index.js`; script `build` com os dois `tsc`.
- `packages/shared/tsconfig.json`: comentário explicando que front e API leem `src/` direto; `rootDir: src`, `declaration: true`, `types: []`.
- `packages/shared/tsconfig.test.json`: checagem de tipos dos testes, sem gerar nada.
- `packages/shared/test/pacote.test.ts`: os 5 cenários (`criarHost`, `resolverOPacote`, `checarImportDeTipoSemDist`, `listarExportsDeValor`).
- `packages/shared/src/index.ts` e `packages/shared/src/projeto.ts`: o que o pacote exporta (só tipos).
- `README.md`: seção "Como rodar" sem o passo de build obrigatório, com a explicação da T-017.
- `apps/api/tsconfig.json` (`nodenext`) e `apps/web/tsconfig.json` (`bundler`): as opções reais que o teste lê para resolver o pacote.

## Exercícios

1. **Siga o import.** Rode `npx tsc --noEmit --traceResolution -p apps/api | Select-String "site-apresentacao/shared"` (ou `grep` no Bash) e encontre as linhas em que o TypeScript lê o `package.json` do shared e escolhe o arquivo. Depois troque, só na sua cópia, `types` de volta para `./dist/index.d.ts`, apague `packages/shared/dist/` e rode de novo: em que linha a resolução falha? Desfaça a troca no fim.
2. **Quebre a regra de propósito.** Acrescente `export const VERSAO = 1;` em `packages/shared/src/index.ts` e rode `npm test -w packages/shared`. Qual teste falha e qual a mensagem? Agora explique, com as suas palavras, o que aconteceria em tempo de execução se a API fizesse `import { VERSAO } from '@site-apresentacao/shared'` num clone sem `dist/` (dica: o `default` aponta para onde?). Desfaça a mudança.
