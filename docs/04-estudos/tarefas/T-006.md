# Diário de estudo — T-006

## O que foi feito

Até a T-005, quem conferia se o projeto estava saudável era só a máquina de quem trabalhava: alguém precisava lembrar de rodar o validador, o lint e os testes antes do push. A T-006 criou a **integração contínua (CI)**: um arquivo, `.github/workflows/ci.yml`, que manda o **GitHub Actions** subir uma máquina Linux limpa a cada push ou pull request para a `main`, baixar o código e rodar as mesmas verificações que rodamos localmente. Se alguma falha, o "check" do commit fica vermelho no GitHub.

As etapas, na ordem em que rodam:

1. baixar o código (`actions/checkout`);
2. validar a estrutura do projeto (`python3 scripts/validar_estrutura.py`);
3. instalar o Node.js 24, com cache do npm (`actions/setup-node`);
4. instalar as dependências (`npm ci`);
5. lint (`npm run lint`);
6. build, que confere os tipos (`npm run build`);
7. testes unitários e de rotas da API (`npm test`);
8. instalar o Chromium do Playwright (`npx playwright install --with-deps chromium`);
9. testes de aceitação no navegador (`npm run test:e2e`);
10. só se algo falhou: guardar o relatório do Playwright para baixar depois.

Cada etapa tem um comentário em português explicando o que faz (critério da tarefa, porque o projeto também é material de estudo). O README ganhou a seção "Integração contínua (CI)".

Quem implementou foi o **devops** (tag `infra`). No caminho houve três decisões, tomadas pelo orquestrador por delegação do George:

- **D1**: o repositório é privado e não há o `gh` instalado, então o orquestrador não consegue ler o resultado do Actions. Escolha: **simular o CI localmente** (instalação limpa + os mesmos comandos) e deixar a confirmação "verde no GitHub" para o George. Por isso o critério 4 continua sem marcar.
- **D2**: o devops notou que nenhuma etapa conferia os **tipos** do TypeScript. Escolha: acrescentar `npm run build` antes dos testes.
- **D3**: depois da revisão, aplicar três melhorias baratas: o validador vira a primeira verificação (antes de instalar qualquer coisa), `concurrency` cancela execuções antigas e o README aponta para o CI. Fixar as actions por SHA ficou para o futuro.

## Conceitos

- **integracao-continua-com-github-actions**: um *workflow* é um arquivo YAML em `.github/workflows/` que diz **quando** rodar (`on:` push e pull request para `main`), **onde** (`runs-on: ubuntu-latest`) e **o quê** (`steps:`, cada um com `run:` para um comando ou `uses:` para uma *action* pronta, como `actions/checkout@v7`). *Por quê aqui:* o fluxo do projeto faz merge local e `git push origin main`; o CI é a segunda opinião, numa máquina limpa, que pega o "na minha máquina funciona" (dependência esquecida, arquivo não commitado, diferença Windows × Linux).
- **falhar-cedo-na-ordem-das-etapas**: as etapas vão da mais rápida para a mais lenta. *Por quê aqui:* se a estrutura de docs estiver quebrada, não faz sentido instalar 441 pacotes e baixar um navegador para descobrir isso no fim. O validador só precisa do Python (que já vem na máquina do GitHub), por isso foi para logo depois do checkout (D3). Resposta mais rápida e menos minutos gastos.
- **npm-ci-e-cache-de-dependencias**: `npm ci` instala **exatamente** o que está no `package-lock.json` e falha se o lock estiver desatualizado em relação ao `package.json`; `npm install` pode atualizar o lock. Já o `cache: npm` do `setup-node` guarda a pasta de downloads do npm (`~/.npm`) entre execuções, usando o lock como chave. *Por quê aqui:* o CI precisa ser **reprodutível** (mesmas versões que passaram localmente) e rápido (enquanto o lock não muda, os pacotes vêm do cache, não da internet).
- **checagem-de-tipos-com-tsc**: o Vitest só **transpila** o TypeScript (tira os tipos e roda o JavaScript), sem conferir se os tipos batem; o lint deste projeto também não usa informação de tipos. Quem confere é o compilador, `tsc`, que roda dentro do `npm run build`. *Por quê aqui:* a prova da T-005 de que front e API compartilham o tipo `Projeto` (`expectTypeOf`) **só falha no build**, com `npm test` verde. Sem a etapa 6 (D2), um erro de tipo chegaria à `main` com o CI verde. De quebra, o build confirma que front e API compilam para produção (pré-requisito do deploy, T-013).
- **concurrency-no-github-actions**: `concurrency.group` junta execuções da mesma referência (`ci-${{ github.ref }}`: a branch num push, o PR num pull request); com `cancel-in-progress: true`, um push novo cancela a execução antiga ainda em andamento. *Por quê aqui:* o repositório é privado e tem minutos gratuitos limitados; só o resultado do commit mais recente importa.
- **permissoes-minimas-do-token**: o GitHub entrega a cada execução um token automático; `permissions: contents: read` limita esse token a ler o código. *Por quê aqui:* o CI não precisa escrever nada no repositório, então não deve poder (princípio do menor privilégio). Também não há segredo nenhum no arquivo: se um dia precisar, entra como *secret* do repositório, nunca no YAML (RNF de segredos).
- **artefatos-de-diagnostico-em-falha**: `if: failure()` faz uma etapa rodar só quando alguma anterior falhou; `actions/upload-artifact` guarda arquivos para baixar na página da execução (aqui por 7 dias). *Por quê aqui:* quando um teste e2e falha numa máquina remota, você não tem o navegador na sua frente; o relatório do Playwright, com capturas e rastro (`trace: 'on-first-retry'`), mostra o que aconteceu. `timeout-minutes: 15` complementa: se o servidor do e2e travar, o job é cancelado em vez de consumir minutos.
- **verificar-antes-de-concluir**: na D1, como não dava para ler o status do GitHub, o devops e o qa **simularam** o CI num clone limpo da branch, fora do repositório, com `CI=true` e na mesma ordem do workflow; o YAML foi conferido com PyYAML e `actionlint`. *Por quê aqui:* é a evidência possível sem tocar em credenciais (a opção de usar o token salvo do git foi descartada). O limite fica escrito: a simulação rodou no Windows, e o Ubuntu (`python3` do sistema, bibliotecas do `--with-deps`) só é exercitado no GitHub. Por isso o critério 4 continua **sem marcar** até o George confirmar.
- **tipos-de-teste-unitario-rota-e2e**: o CI roda as três camadas em etapas separadas: `npm test` (Vitest nos componentes e Supertest nas rotas da API) e `npm run test:e2e` (Playwright no navegador). *Por quê aqui:* separar as etapas mostra no GitHub **qual** camada falhou, e os testes de navegador, os mais lentos, ficam por último. A config do Playwright muda de comportamento com `CI=true`: proíbe `test.only` esquecido e repete até 2 vezes um teste instável.

## Onde aparece no projeto

- `.github/workflows/ci.yml`: o workflow inteiro; o cabeçalho lista a ordem das etapas e os comandos para reproduzir localmente.
- `README.md`: seção "Integração contínua (CI)", depois de "Comandos".
- `scripts/validar_estrutura.py`: o validador (só biblioteca padrão do Python: `argparse`, `sys`, `pathlib`), por isso roda antes do `npm ci`.
- `package.json` (raiz): o campo `engines` (Node 24, a versão usada no `setup-node`) e os scripts `lint`, `build`, `test` e `test:e2e` que o CI chama.
- `package-lock.json`: chave do cache e fonte da instalação do `npm ci`.
- `e2e/playwright.config.ts`: comportamento com `CI=true` e as pastas `e2e/playwright-report/` e `e2e/test-results/` guardadas pela etapa 10.
- `eslint.config.mjs`: a configuração única do lint (ADR-0002) usada pela etapa 5.
